==================================================
EL RETO
==================================================

DE LA RESPUESTA EN TEXTO A LA INTERFAZ QUE ACTÚA

Caso de uso libre, siempre dentro de servicios o productos financieros. Cada equipo elige el problema concreto.

HOY: EL ASISTENTE RESPONDE
- Un muro de texto que la persona tiene que interpretar.
- La misma pantalla para cualquier intención.
- Para actuar, la persona se va a otra sección.

AQUÍ: EL AGENTE CONSTRUYE LA UI
- La pantalla se arma según la intención detectada.
- Componentes propios: simuladores, tablas, formularios.
- Lo que la persona toca regresa al modelo como contexto.


==================================================
OBJETIVO
==================================================

UNA EXPERIENCIA QUE SE REDISEÑA A SÍ MISMA

PASO 01: INTERPRETAR LA INTENCIÓN
El agente entiende qué quiere lograr la persona y con qué contexto.

PASO 02: GENERAR LA INTERFAZ
Decide qué componentes mostrar y los transmite mediante A2UI o un protocolo equivalente.

PASO 03: EJECUTAR LA ACCIÓN
La interacción con esa UI dispara nuevas acciones y vuelve a cambiar la experiencia.

El LLM es el centro de la experiencia, no un chat pegado a un dashboard.

DOMINIO

TERRITORIO: SERVICIOS Y PRODUCTOS FINANCIEROS

- Banca personal: cuentas, movimientos, control de gasto.

==================================================
BASE TÉCNICA COMÚN
==================================================

TRES PIEZAS QUE NO SON NEGOCIABLES

1. LLM — El modelo al centro
Un LLM debe ser parte central de la experiencia: interpreta, decide y orquesta.

2. MCP — Datos, herramientas y acciones
Model Context Protocol para exponer al modelo los datos, las herramientas y las acciones que el equipo construyó.

3. A2UI — La interfaz viaja
Agent-to-UI, o un protocolo equivalente, para representar y transmitir la interfaz que genera el agente.


==================================================
CÓMO SE CONECTA
==================================================

ARQUITECTURA DE REFERENCIA

Usuario (expresa una necesidad)
  → Agente / LLM (interpreta intención y contexto)
  → MCP (datos, herramientas y acciones)
  → A2UI (describe la UI que se renderiza)
  → Componentes (UI propia, viva y accionable)

La interacción regresa al agente como contexto (flujo en bucle).

El ciclo se cierra. No basta con generar una pantalla una vez: cada interacción con la UI generada debe volver al agente y producir nuevas acciones o una nueva interfaz.


==================================================
REGLAS — LO QUE CADA EQUIPO CONSTRUYE
==================================================

1. Sus propios componentes
No se entrega biblioteca de UI. El sistema de componentes que el agente invoca lo diseña y programa el equipo.

2. Sus propios datos y APIs
Los datos y servicios se crean o se integran por los participantes: sintéticos, simulados o de fuentes abiertas.

3. Al menos un flujo accionable
Un flujo donde la persona interactúe con la UI generada y esa interacción produzca un cambio real.

4. Libertad de stack
Cualquier lenguaje, framework, modelo o proveedor de infraestructura adicional está permitido.

Aplica por igual a todos los equipos: es la base que hace comparables las soluciones.


==================================================
EVALUACIÓN — CÓMO SE REPARTEN LOS PUNTOS
==================================================

- Cumplimiento y utilidad para el usuario: 25%
- Calidad y adaptabilidad de la UI generada: 20%
- Calidad de la solución de IA: 15%
- Arquitectura e ingeniería: 15%
- UX y diseño: 10%
- Innovación: 10%
- Presentación: 5%

Resumen:
- 45%: resolver algo útil y qué tan buena y adaptable es la UI.
- 30%: la ingeniería: uso del LLM, del contexto, de MCP y de A2UI.
- 15%: UX, diseño e innovación.
- 5%: la presentación. La demo importa, pero no salva una solución.

Elijan un problema pequeño y resuélvanlo completo.
